# 协作与需求流程规则

本文件用于约束代理在当前仓库中的工作方式。凡是任务涉及需求拆解、方案判断、文档更新、跨模块改动、vibecoding 协作或不确定范围判断，都必须先读取本文件。

## 总体工作方式

- 先读本地文档、计划、现有代码与最近实现，再给方案或改代码。
- 不脱离当前架构重新设计。
- 如果本地上下文不足以判断方案，先检索官方示例、成熟实现或同类开源项目，再给结论，并说明本地事实与外部参考的区别。
- 每个方案都应说明任务边界、文件归属、数据流、失败路径和验证方式。
- 优先把大目标拆成可单独验收的小任务。
- 默认选择能减少未来维护成本的做法：少依赖、少魔法、少全局状态、少隐式约定。
- 不清楚的不能瞎编，应追问用户。

## 需求文档

- 每次新增或修改功能，必须同步更新 `design-input` 下的需求文档。
- 如果 `design-input` 中没有对应文件，先创建一个聚焦当前需求的 Markdown 文件。
- 需求文档至少包含目标、范围、数据边界、交互规则、错误处理和后续预留。
- 不要把实现细节、临时代码计划或内部任务编号暴露成面向用户的产品文案。

## 代码生成护栏

- 新增功能前先查找可复用组件、工具函数、Supabase helper 和既有路由模式。
- 不为了快速实现复制大段相似代码。
- 业务逻辑、数据访问、UI 展示应尽量分层。
- 避免把请求、解析、状态处理和复杂 UI 全塞进一个大组件。
- AI 生成的代码必须保留可读命名、明确类型、最小副作用和必要错误处理。
- 不要留下 `TODO`、`Mock`、临时脚本或难以解释的魔法常量。

## 红线

- 不把后台能力塞回公开主站仓库，除非用户明确要求重新设计架构。
- 不绕过既定数据流：公开提交不抓 Bilibili，公开读取不抓 Bilibili，审核抓取只在后台延迟发生。
- 不引入 Python、`child_process` 或第三方 Bilibili wrapper 来绕开当前 Node-only 约束。
- 不在 `globals.css` 写业务组件样式。
- 不把一次性页面样式沉淀成全局规则。
- 不用“先跑起来以后再说”作为长期方案；临时取舍必须写清楚后续清理点和验收条件。

## 渐进式加载维护规则

- 根 `AGENTS.md` 只保留仓库级高优先级规则、加载路由和常用命令。
- 模块细则放在 `docs/agent-rules/*`。
- 新增稳定规则时，优先写入最相关的子文档，不要把根 `AGENTS.md` 写回大段细则。
- 当某类任务反复出错时，先更新对应子文档，再在根 `AGENTS.md` 的加载路由中补充触发条件。
- 如果规则只适用于某个子目录，优先考虑在该子目录新增更近的 `AGENTS.md` 或 `AGENTS.override.md`，不要污染根规则。

## 输出要求

- 简单任务直接给结论和关键验证结果。
- 复杂任务按模块说明变更、验证和风险。
- 最终回复必须说明是否运行了 `npm run type-check`，以及结果或未运行原因。
- 如果没有运行必要验证，不能声称任务已完成或可提交。
